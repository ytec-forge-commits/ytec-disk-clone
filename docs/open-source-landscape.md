# 類似オープンソース調査と採用判断

調査日: 2026-08-08

この文書は、正式版1.0.0再設計に先立つ設計比較を記録する。参照先のコードは
製品へコピーしておらず、新しい依存関係も追加していない。本製品は2026年8月20日
からApache-2.0で公開するが、この調査時点のclean-room方針と由来確認を維持し、
採用対象は一般化した設計上の知見だけとする。ライセンス互換だけを理由に第三者
コードを取り込まない。

## 絞り込んだプロジェクト

### Rufus

- 参照: <https://github.com/pbatard/rufus>
- 解決する問題: Windows上での起動USB作成、フォーマット、イメージ書込み。
- アーキテクチャ: 管理者権限で動くWindowsネイティブのポータブルアプリが、対象列挙、
  排他取得、構成、書込み、検証、ログをローカルで完結させる。
- 主な技術・依存: C/C++、Win32、各種ブートローダー／ファイルシステム処理。
  GPL-3.0のため、コードやバイナリは再利用しない。
- 継続状況: 2026-04-30に4.14が公開されており、継続開発中。
- 再利用する設計: 危険な対象を既定一覧から外す、詳細操作でだけ候補を広げる、
  対象の排他取得、詳細ログ、ダウンロード物の厳格な検証。
- 避ける設計: 内部ディスクを扱わないという製品固有制限、隠しキー操作、
  大きなネイティブ単体実装、GPLコードの流用。

### Rescuezilla

- 参照: <https://github.com/rescuezilla/rescuezilla>
- 解決する問題: Clonezilla系のクローン／イメージ機能を、Live USB上の分かりやすい
  GUIから直接利用できるようにする。
- アーキテクチャ: Ubuntu Live環境のPython/GTKフロントエンドが、Partclone、
  qemu-nbdなど複数の外部ツールを調停する。
- 主な技術・依存: Python、GTK、Ubuntu、Partclone、Clonezilla互換形式、qemu-nbd。
  GPL-3.0のため、コードや同梱部品は再利用しない。
- 継続状況: 2026-05-16に2.6.2が公開され、夜間の統合試験も案内されている。
- 再利用する設計: 起動環境だけで処理を完結する直接操作UI、短いウィザード、
  イメージ検証を独立した操作として見せること、複数レイアウトの試験マトリクス。
- 避ける設計: Linux Live環境への置換、外部コマンドの連鎖、広すぎる救出ツール群、
  形式互換性を優先して製品境界を拡大すること。同プロジェクトは小容量ディスクへの
  自動縮小を未完了としており、そのまま設計根拠にはできない。

### FOG Project

- 参照: <https://github.com/FOGProject/fogproject>
- 解決する問題: 多数PCをPXE起動し、サーバーからイメージ取得、配布、管理する。
- アーキテクチャ: Web UI／サーバー、PXE、LinuxベースのFOS実行環境、Partcloneを
  分離したクライアント・サーバー構成。
- 主な技術・依存: PHP/Web、Linux、Buildroot、iPXE、Partclone、Zstandardなど。
  GPL-3.0のため、コードや実行部品は再利用しない。
- 継続状況: 2026-06-15にも1.5.10系の自動リリースがあり、継続開発中。
- 再利用する設計: 操作計画と実行環境の分離、取得前の保存先空き容量確認、
  ディスクserialを含む対象識別、縮小時に後続パーティションを配置し直す考え方。
- 避ける設計: サーバー、PXE、登録端末、予約タスク、ネットワーク保存を製品へ持ち込む
  こと。正式版が廃止する予約ジョブ方式と方向が逆である。

### UrBackup

- 参照: <https://github.com/uroni/urbackup_backend>
- 解決する問題: Windowsを含む複数OSのファイル／イメージバックアップを、
  クライアント・サーバー方式で継続運用する。
- アーキテクチャ: C/C++バックエンド、クライアント／サーバー、プラグイン、
  ネットワーク転送、Windows Snapshot処理を組み合わせる。
- 主な技術・依存: C/C++、VSSを含むOS別処理、DB、Web／ネットワーク、複数plugin。
  AGPL-3.0のため、コードやライブラリは再利用しない。
- 継続状況: 2026-04-23に2.5.30 clientが公開され、devブランチも更新されている。
- 再利用する設計: VSS取得とペイロード処理を分離すること、処理単位を有界にすること、
  OS別adapterを共通契約の外側へ置くこと。
- 避ける設計: 常駐サービス、ネットワーク転送、サーバーDB、plugin群、増分履歴を
  1.0.0へ持ち込むこと。

## Y-TEC Tsumugi Driveへの結論

### 技術選定

- MSVC C++20のWindows x64ネイティブ構成を維持する。
- OS機能はVSS、Win32ディスクI/O、Windows CNG、BCDBoot、ADK/WinPEへ限定する。
- 外部依存は承認済みのZstandard 1.5.7とArgon2 20190702だけを固定する。
- GPL/AGPL系のPartclone、Clonezilla、Rufus、FOG、UrBackupをリンク、同梱、呼出し
  しない。調査した実装コードを転記しない。

### システム構成

```text
Windows UI / WinPE UI
  -> OperationPlan と最終確認
  -> OS別の読取り専用Source Session
  -> 共通Clone / Tsumugi / Rescue / BootRepair Engine
  -> OS別の検証済みTarget Transaction
  -> flush・読戻し・メタデータ最終commit
  -> OperationResult
```

Rufusからは候補制限と対象保護、Rescuezillaからは直接操作の分かりやすさ、FOGからは
計画と実行の分離だけを取り入れる。ネットワーク、予約ジョブ、Linux実行環境、
汎用pluginは加えない。

### MVPの境界

正式版要件を削らず、実装可能な縦切りで段階化する。

1. Windows／PEの通常モード直接クローンと`.tsumugi`完全検証経路を、合成対象で
   端から端まで通す。
2. 通常経路と同じ安全境界へ縮小移行、MBR維持、MBRからGPTを接続する。
3. 対象ディスクだけを選ぶ自動起動修復、救出、中断再開を接続する。
4. 固定Microsoft取得物の同意、署名、版、SHA-256検証を伴うADK導入と、
   2パーティションUSB／ISO作成を接続する。
5. VM、静的解析、ASan、失敗注入、UI/DPI、配布候補監査を終えてから実機受入へ進む。

### 承認との関係

この結論は、利用者が承認済みの「Y-TEC Tsumugi Drive 1.0.0正式版再設計計画」の
技術選定、MVP範囲、開発順序を変更しない。新依存、ネットワーク機能、対応形式、
公開範囲を増やす判断が必要になった場合は、改めて承認を得る。
