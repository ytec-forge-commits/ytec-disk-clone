# 縮小移行モード

更新日: 2026-08-09

## 目的

縮小移行モードは、コピー元の総容量より小さいディスクへ、選択した内容と安全余白が
収まる場合だけ移行する機能である。コピー元のパーティションをその場で縮小せず、
コピー元は読取り専用のまま、コピー先だけへ新しいレイアウトとファイルシステムを
作成する。

正式版では、直接クローンと`.tsumugi`イメージ作成・復元の両方で提供する。

> 現在は既存のNTFS縮小部品と`.tsumugi`共通形式を統合中である。通常／縮小、
> Windows／データ専用、Windows／PEの全製品経路はまだ完成していない。

## 対応方針

| 項目 | 通常モード | 縮小移行モード |
|---|---|---|
| 直接クローン | 原則として元サイズを保つ | コピー先だけへ小さい区画を再作成 |
| イメージ作成 | `.tsumugi`へRAW／used-rangeを保存 | 同じ`.tsumugi`へファイル単位ペイロードと最小容量を保存 |
| イメージ復元 | 元レイアウトまたは安全な拡張 | 計算済み最小容量以上へ再構成 |
| Windowsディスク | 必須システム領域を含める | 必須領域を自動選択し、解除不可 |
| データ専用ディスク | 選択区画を複製 | 選択区画を小さいレイアウトへ再作成 |

NTFS、exFAT、FAT32は縮小対象とする。対応外ファイルシステムは元サイズのRAWコピー
だけを許可し、縮小しない。512系↔4Knはファイル単位移行でだけ条件付き対応する。

MBR元はMBR維持またはMBR→GPTを選べる。GPT→MBRは対応しない。

## 容量計画

各ファイルシステムの最小必要量、メタデータ、アラインメント、安全余白、必須
システム領域を先に確保する。コピー先が最小必要容量を1バイトでも下回る場合は、
最初の対象書込み前に停止する。

余剰容量は次から選ぶ。

- `自動配分`（既定）: 各区画の最小必要量を確保した後、元サイズ比で配分
- `未割当のまま`: 必要領域だけを作り、残りを未割当として残す

丸めは対象の論理／物理セクターと1MiB境界を考慮し、加算・乗算・比率計算の
オーバーフローを拒否する。

## Windows必須領域

Windowsパーティションを選択した場合は、検出した次を自動選択し解除不可にする。

- GPT／UEFI: ESP、MSR、Windows、必要な回復領域
- MBR／BIOS: Activeシステム領域、Windows、必要な回復領域

コピー先の内容移行後にだけ、対象側へBCD／ブートファイル／WinREを必要範囲で
構成する。起動成功とは表示せず、システムクローンは「検証完了・換装待ち」とする。

データ専用ディスクではESP、Active、BCD、WinREを作成しない。

## 安全境界

- コピー元は書込みメソッドを持たないReaderからだけ渡す。
- Windows版では同一VSS Snapshot set、PE版では同一read-only epochに固定する。
- コピー先はRAWに限定せず、既存の基本GPT／MBR／NTFS等も候補にできるが、
  対象要約と大文字`OK`の後にだけ全体を消去・再構成する。
- コピー先のモデル、容量、接続方式、シリアル末尾、パーティション図を確認前と
  実行直前に再照合する。
- Dynamic Disk、Storage Spaces、WindowsソフトウェアRAID、不明なRAID、
  解析不能レイアウトは開始しない。
- USBメモリと起動中レスキューUSB全体を対象から除外する。
- 救出モードで欠損がある場合は縮小・形式変換を行わない。
- 失敗や取消では完成レイアウトをcommitせず、未完了対象を成功表示しない。

## `.tsumugi`との関係

縮小用データも単一`.tsumugi`コンテナへ格納する。一時的な別形式や第三ディスク上の
予約引継ぎは正式版の操作モデルにしない。マニフェストへ、各区画の元範囲、最小容量、
復元後サイズ、ファイルシステム方針、必須システム領域を記録し、復元時に再検証する。

WIM payloadはファイルのバイトストリームとして実長を保存し、セクター境界への
paddingを要求しない。未対応FSの`exact RAW`だけは元区画全体を保持し、Source／
payload／Targetを論理セクターへ整列する。未知encodingや不正境界はfail-closedとする。

Windows向けの現在の最小sliceは、複数NTFSを同一VSS Snapshot setへ結合し、Snapshot
デバイスだけを署名確認済みSystem32 DISMへ渡す製品Platform Adapterまで実装済みで
ある。コピー元identity、partition extent、Volume GUID、Snapshot IDを一つの状態Hashへ
結合し、静的`exact RAW`は読取り専用handleの前後fingerprint一致を要求する。WIM staging
とscratch／checkpoint／logは既存canonical guardの外へ出さず、Snapshot削除成功後だけ
Controllerが`.tsumugi`完成名をcommitする。製品UI接続、実VSS／実DISM／物理I/O試験、
exFAT／FAT32／BitLocker対応は未完了であり、これらはI/O前にfail-closedとする。

旧MigrationEngineから再利用できるのは、Microsoft署名を前後確認するDISM実行と、
固定したWIMの長さ／SHA-256検証などの下位部品である。旧bundle captureは`.dcmig`を
直接作成しSnapshot IDを製品契約へ結合しないため使用しない。旧volume applyも
DISM成功後の実ファイル読戻しと新しい最終commit契約を持たないため、そのまま
製品Adapterとはせず、不足する再識別・読戻し境界を実装してから接続する。

直接クローンで内部的な一時保存が必要な場合も、その処理は現在の実行セッションと
1件のCheckpointにだけ結び付ける。後から自動実行する予約データへ転用しない。

## 検証計画

- 1バイト不足、境界一致、大容量余剰、複数区画、丸め、オーバーフロー
- Windows／データ専用、GPT／MBR、MBR→GPT
- NTFS／exFAT／FAT32、未対応FS混在
- Windows版VSS、WinPE read-only Source
- 直接クローン、イメージ作成、全体復元、個別復元
- コピー元不変、対象差替え、取消、読戻し失敗、最終commit失敗
- 512／512e／4Knの許可・拒否境界
- コピー元を外した後のBIOS／UEFI／Secure Boot VM起動

既存の旧形式やWIMを使ったVM証跡は、ファイル単位移行部品の根拠として再利用する。
新しい直接経路と`.tsumugi`経路で再回帰するまで、1.0.0の合格とは扱わない。
